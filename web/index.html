배포 현황 보드

이 보드 읽는 법— Jira 작업(이슈 키) 하나가 지금 어디까지 나갔는지를 레포별로 보여 줍니다.

배포 흐름과 5개 열

  1. 브랜치 — 작업 브랜치(PILLDOC-xxxx)만 있고 PR 이 없음. 작업 중이거나 머지 뒤 안 지운 브랜치.
  2. PR — PR 이 열려 있음(Draft 는 꼬리표).
  3. develop — develop 브랜치에 머지됨. 아직 스테이징 브랜치(deploy/prod, pillcheck 는 deploy/dev)에는 없음.
  4. 스테이징 — 스테이징 브랜치에 머지돼 GitHub Actions 가 Azure staging 슬롯(pillcheck 는 staging.pillchk.com)에 올림. 아직 운영 사용자는 못 봄.
  5. 운영 — staging → production swap(pillcheck 는 deploy/prod 배포 run 성공)이 끝나 실제 서비스에 반영됨.

한 이슈가 여러 단계에 걸쳐 있으면 가장 높은 단계에 둡니다.

픽셀 사무실

  • 방 5개가 위 다섯 단계이고, 캐릭터 하나가 이슈 하나입니다(머리 위 숫자 = 이슈 번호). 캐릭터를 누르면 브랜치·PR·커밋 목록과 Jira 링크가 열립니다.
  • 새로고침 뒤 단계가 바뀐 이슈는 다음 방으로 걸어가고, 새 이슈는 왼쪽 입구로 들어오며, 목록에서 빠진 이슈는 오른쪽으로 나갑니다.
  • 방 자리(18명)보다 이슈가 많으면 방 이름 옆에 「+N 자리 없음」으로 표시됩니다. 헤더의 「보기」에서 픽셀 대신 표(5열 보드)나 둘 다를 고를 수 있고, 표에는 자리와 상관없이 전부 나옵니다.

레포 위 세 칸

  • develop — develop 최신 커밋. 「N개 커밋이 develop 에만」은 아직 스테이징 브랜치로 안 넘어간 커밋 수.
  • 스테이징 — 스테이징 브랜치 최신 커밋. 「N개 커밋이 스테이징에만」은 swap(또는 운영 배포)을 기다리는 커밋 수.
  • 운영 — 오른쪽 기준으로 정한 운영 SHA 와 마지막 swap 시각·실행자(브랜치 모드는 배포 run).

꼬리표

  • 「develop 에만 있는 커밋 있음(운영 미반영)」 — 같은 이슈의 추가 커밋이 develop 에 남아 있음.
  • 「운영 반영 뒤 추가 커밋이 스테이징에 있음」 — 운영에 한 번 나갔지만 후속 수정이 swap 대기.
  • 「stg/ 브랜치」 — 스테이징 검증용 브랜치가 있음. 「Draft PR」 — 열린 PR 이 Draft.

정보를 어떻게 모으나

AI 는 쓰지 않습니다. 실행한 사람의 git·gh·az 로그인으로 아래를 읽기만 합니다(쓰기·배포·swap 실행 없음).

  1. git(로컬 클론) — 레포마다 projects/<repo> 클론에서 fetch --prune 뒤 원격 브랜치 전체 목록(이름·끝 커밋·작성자·날짜)과 세 브랜치(develop·스테이징·운영 추정 SHA) 사이 커밋 차이를 봅니다. 차이는 --cherry-pick 비교라 cherry-pick 으로 이미 넘어간 같은 패치는 제외하고, 머지 커밋도 제외합니다. 클론이 없으면 받아 옵니다.
  2. GitHub PR — gh pr list 로 상태 무관 최근 300건(번호·제목·base·머지 커밋·Draft·갱신 시각).
  3. GitHub 배포 run — 배포 워크플로(deploy.yml·ci.yml)가 배포 브랜치에서 돈 최근 30건(커밋 SHA·성공 여부·끝난 시각).
  4. Azure swap — App Service 활동 기록 최근 90일에서 slotsswap 성공 이벤트(시각·실행자). 사람과 자동 처리기가 같은 swap 에 둘 다 남기므로 3분 안의 것은 하나로 합치고 사람 쪽을 남깁니다.
  5. 이슈 키 — 브랜치 이름·PR 제목·커밋 메시지에서 PILLDOC-/PHAI-/MOBILE-/PA2-/PI-숫자 꼴만 뽑습니다. 키가 없는 커밋·브랜치는 어느 이슈에도 안 붙어 화면에 없습니다. Jira 자체는 읽지 않고 링크만 겁니다.

레포 두 종류 — swap 모드(adminsite·pilldocsite·agentapiv2·adpssite): deploy/prod 머지 → Actions 가 staging 슬롯에 올림 → 사람이 swap. 브랜치 모드(pillcheckver2frontend, Vercel): deploy/dev 머지가 스테이징, deploy/prod 머지가 곧 운영 배포라 swap 이 없습니다.

갱신

  • 서버가 30초마다 레포 변경(브랜치 끝 커밋·최근 PR 갱신 시각·브랜치 모드는 배포 run 상태)을, 2분마다 Azure swap 을 가볍게 확인해 바뀐 레포만 다시 수집합니다. 이 화면은 10초마다 결과를 받아 자동 반영하고, 단계가 바뀐 캐릭터가 걸어갑니다. 「새로고침」은 전체 즉시 재수집(약 1~2분).
  • 웹훅(GitHub·Azure 가 바로 알려 주는 방식)은 외부에서 접근되는 주소가 필요해 지금은 쓸 수 없습니다.

대상 레포: adminsite · pilldocsite · agentapiv2 · adpssite · pillcheckver2frontend. 필독에이전트 v2(TMA S3 릴리스)는 아직 없습니다.

단계를 정하는 기준

이슈 키 하나에 붙은 브랜치·PR·커밋을 모아 아래 규칙으로 단계를 매기고, 여러 개면 가장 높은 단계를 씁니다.

  • 브랜치 — 키가 든 원격 브랜치가 있음.
  • PR — 키가 든 PR 이 OPEN(Draft 포함).
  • develop — develop 대상 PR 이 MERGED, 또는 키가 든 커밋이 develop 에만 있음.
  • 스테이징 — 스테이징/운영 브랜치 대상 PR 이 MERGED, 또는 키가 든 커밋이 스테이징에만 있음(운영 SHA 에 없음).
  • 운영 — 그 PR 의 머지 커밋이 운영 SHA 의 조상(merge-base --is-ancestor). 단 같은 이슈의 추가 커밋이 스테이징에만 남아 있으면 스테이징으로 내리고 꼬리표를 답니다.

운영 SHA — swap 모드는 Azure 가 운영에 뜬 커밋을 알려 주지 않아 「마지막 swap 직전에 성공한 배포 run 의 커밋」으로 추정합니다(swap 되돌림·포털 수동 배포는 못 잡음). 브랜치 모드는 운영 브랜치의 마지막 성공 배포 run 입니다. 근거는 레포 아래 접힌 영역에 있습니다.

PR 을 닫기만 하고 머지하지 않으면 PR 단계가 풀려 브랜치만 남습니다. 머지된 PR 의 브랜치를 안 지우면 「브랜치」열에 계속 보입니다.

무엇이 어떤 순서로 보이나

  • 마지막 활동 = 그 이슈의 브랜치 끝 커밋·PR 갱신·커밋 날짜 중 가장 최근. 열 안 순서와 픽셀 방 자리(앞자리부터)는 이 값의 최신순입니다.
  • 기간 필터(기본 30일)는 마지막 활동 기준입니다. 오래된 운영 반영 건이 안 보이면 「전체」로 바꿉니다.
  • 제목은 가장 최근 PR 제목, 없으면 커밋 메시지, 없으면 브랜치 끝 커밋 메시지입니다.
  • 표는 열마다 40개까지 보여 주고 나머지는 「+N개 더」, 픽셀 방은 18자리를 넘으면 「+N 자리 없음」입니다. 검색으로 좁히면 됩니다.
  • 검색은 이슈 키와 제목에 대해 부분 일치이며 타이핑이 멈춘 뒤 적용됩니다.
  • 레포 순서는 제목 왼쪽 손잡이(⠿)를 끌어 다른 레포 위·아래에 놓거나 ▲▼ 로 바꾸고, ▾ 로 레포를 접으면 헤더와 단계별 건수만 남습니다. 순서·접힘은 이 브라우저에 기억됩니다.
