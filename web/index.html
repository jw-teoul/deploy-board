배포 현황 보드

이 보드 읽는 법— Jira 작업(이슈 키) 하나가 지금 어디까지 나갔는지를 레포별로 보여 줍니다.

배포 흐름과 5개 열

  1. 브랜치 — 작업 브랜치(PILLDOC-xxxx)만 있고 PR 이 없음. 작업 중이거나 머지 뒤 안 지운 브랜치.
  2. PR — PR 이 열려 있음(Draft 는 꼬리표).
  3. develop — develop 브랜치에 머지됨. 아직 운영 브랜치(deploy/prod)에는 없음.
  4. 스테이징 — deploy/prod 에 머지돼 GitHub Actions 가 Azure staging 슬롯에 올림. 아직 운영 사용자는 못 봄.
  5. 운영 — staging → production swap 이 끝나 실제 서비스에 반영됨.

한 이슈가 여러 단계에 걸쳐 있으면 가장 높은 단계에 둡니다.

픽셀 사무실

  • 방 5개가 위 다섯 단계이고, 캐릭터 하나가 이슈 하나입니다(머리 위 숫자 = 이슈 번호). 캐릭터를 누르면 브랜치·PR·커밋 목록과 Jira 링크가 열립니다.
  • 새로고침 뒤 단계가 바뀐 이슈는 다음 방으로 걸어가고, 새 이슈는 왼쪽 입구로 들어오며, 목록에서 빠진 이슈는 오른쪽으로 나갑니다.
  • 방 자리(18명)보다 이슈가 많으면 방 이름 옆에 「+N 자리 없음」으로 표시됩니다. 헤더의 「보기」에서 픽셀 대신 표(5열 보드)나 둘 다를 고를 수 있고, 표에는 자리와 상관없이 전부 나옵니다.

레포 위 세 칸

  • develop — develop 의 최신 커밋. 「→ deploy/prod: N개 커밋이 develop 에만」은 아직 운영 브랜치로 안 넘어간 커밋 수(cherry-pick 으로 이미 넘어간 같은 내용은 제외).
  • 스테이징 — deploy/prod 의 최신 커밋. 「→ 운영: N개 커밋이 스테이징에만」은 swap 을 기다리는 커밋 수.
  • 운영(추정) — Azure 는 운영에 어떤 커밋이 떠 있는지 알려 주지 않아서, 마지막 swap 직전에 성공한 배포 run 의 커밋으로 추정합니다. swap 을 되돌렸거나 포털에서 수동 배포했으면 틀릴 수 있습니다(근거는 아래 접힌 영역).

꼬리표

  • 「develop 에만 있는 커밋 있음(운영 미반영)」 — 같은 이슈의 추가 커밋이 develop 에 남아 있음.
  • 「운영 반영 뒤 추가 커밋이 스테이징에 있음」 — 운영에 한 번 나갔지만 후속 수정이 swap 대기.
  • 「stg/ 브랜치」 — 스테이징 검증용 브랜치가 있음. 「Draft PR」 — 열린 PR 이 Draft.

자료 출처와 갱신

  • GitHub: 브랜치·커밋(로컬 클론 git), PR, deploy.yml 실행 기록.
  • Azure: App Service 활동 기록의 slot swap(시각·실행자).
  • Jira 는 링크만 연결합니다(상태는 안 읽음).
  • 서버가 30초마다 레포 변경(브랜치 끝 커밋·PR 갱신)을, 2분마다 Azure swap 을 가볍게 확인해 바뀐 레포만 다시 수집하고, 이 화면은 10초마다 그 결과를 받아 자동 반영합니다(단계가 바뀐 캐릭터가 걸어갑니다). 「새로고침」은 전체를 즉시 다시 수집합니다(약 1분).
  • 웹훅(GitHub·Azure 가 바로 알려 주는 방식)은 외부에서 접근되는 주소가 필요해 지금은 쓸 수 없습니다. 나중에 붙이면 즉시 반영됩니다.
  • 기본 필터는 최근 30일 활동 이슈만 보여 줍니다. 오래된 것은 「전체」로.

대상 레포: adminsite · pilldocsite · agentapiv2 (웹·API, Azure swap 배포). 필독에이전트 v2(TMA S3 릴리스)는 아직 없습니다.
